# 기능 정의서 — 의료기기 유통 플랫폼 (MediTrade)

> **⚠️ 프로젝트명**: MediTrade (잠정 확정 — 동명 의료기기 업체가 다수 존재하여 정식 서비스명은 추후 변경될 수 있음. 현재는 내부 명칭으로 사용)
>
> 본 문서는 플랫폼의 기능을 식별하고 역할·입출력·예외·우선순위(Phase)를 정의한다.
> 기술 구현은 `backend-phase1-setup.md`, 작업 순서는 `PHASE1-TASKS.md`를 참조한다.

---

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 목적 | 의료기기 탐색·문의·거래를 한 곳에서 처리하는 B2B 유통 채널 제공 |
| 범위 | 회원/인증, 상품, 검색, 찜, 문의·견적, 거래, 리뷰, 사업자 인증, 관리자, 알림 |
| 플랫폼 | 웹(Next.js) + 모바일 앱(React Native) — 동일 REST API 공유 |
| 우선순위 | P1(MVP) / P2(확장) / P3(고도화) |

### 용어
- **구매자(Buyer)**: 의료기기를 찾는 기관 담당자
- **판매자(Seller)**: 제조/수입/대리점/중고 업체
- **관리자(Admin)**: 플랫폼 운영자
- **문의(Inquiry)**: 구매자가 특정 상품에 보내는 견적/문의 요청
- **견적(Quote)**: 판매자가 문의에 대해 제시하는 가격/조건
- **거래(Deal)**: 견적 수락 후 진행되는 거래 건
- **미팅(Meeting)**: 구매자가 판매자에게 요청하는 만남(온라인/방문/현장 실사·설치 상담)

## 2. 사용자 역할

| 역할 | 설명 | 가입 조건 |
| --- | --- | --- |
| BUYER | 상품 탐색·문의·거래·리뷰 | 이메일 가입(+선택적 사업자 인증) |
| SELLER | 상품 등록·견적·거래 처리 | 이메일 가입 + **사업자/판매업 신고 인증 필수** |
| ADMIN | 회원/상품 심사, 운영 | 내부 부여 |

## 4. 주요 기능 상세 명세 (Phase 1)

> 형식: 입력 / 처리 / 출력 / 예외(에러코드)

### AUTH-001 회원가입
- **입력**: email, password(8자 이상), name, phone(선택), role(BUYER|SELLER)
- **처리**: 이메일 중복 확인 → 비밀번호 bcrypt 해시 → 회원 생성(status=ACTIVE)
- **출력**: 생성된 회원 id, email
- **예외**: 이메일 중복 409 `CONFLICT` / 입력 형식 오류 400 `VALIDATION_ERROR`
- **비고**: SELLER도 가입은 가능하나, 상품 등록 전 사업자 인증(P2) 필요 정책 가능

### AUTH-002 로그인
- **입력**: email, password
- **처리**: 회원 조회 → 비밀번호 검증 → JWT 액세스 토큰 발급(payload: sub, role)
- **출력**: accessToken, member(id, email, name, role)
- **예외**: 불일치 401 `UNAUTHORIZED` (계정 존재 여부 노출 금지 — 메시지 통일)

### PROD-001 상품 등록
- **입력**: name, modelName(선택), categoryId, conditionType(NEW|USED|REFURBISHED), price(선택), region(선택), description(선택)
- **처리**: 인증·권한(SELLER) 확인 → 상품 생성(sellerId=토큰 사용자, status=ON_SALE)
- **출력**: 생성된 상품(직렬화: BigInt→string)
- **예외**: 미인증 401 / 권한없음 403 `FORBIDDEN` / 입력오류 400 `VALIDATION_ERROR`

### PROD-002 / PROD-003 상품 수정·삭제
- **입력**: productId(+수정 필드)
- **처리**: 상품 조회 → 존재 확인 → 소유자(sellerId == 토큰 사용자) 확인 → 수정/삭제
- **출력**: 수정된 상품 / 삭제된 id
- **예외**: 없음 404 `NOT_FOUND` / 타인 상품 403 `FORBIDDEN`

### SRCH-001 / SRCH-002 상품 목록·검색
- **입력**: page(기본 1), size(기본 20), keyword(선택)
- **처리**: status=ON_SALE 필터 → (keyword 있으면 name/modelName 검색) → 최신순 페이징
- **출력**: items[], total, page, size
- **예외**: 잘못된 페이지 파라미터 400 `BAD_REQUEST`

### PROD-004 상품 상세
- **입력**: productId
- **처리**: 상품 + 이미지 + 카테고리 조회 (선택적으로 조회수 증가)
- **출력**: 상품 상세(이미지/스펙 포함)
- **예외**: 없음 404 `NOT_FOUND`

### (참고) MEET-001 미팅 요청 — P2
- **입력**: sellerId(필수), productId(선택), meetingType(ONLINE|VISIT_SELLER|VISIT_BUYER), purpose(상담/실물확인/데모/설치상담 등), preferredSlots(희망 일시 후보 1~3), message(선택), location 또는 onlineLink(선택)
- **처리**: 인증·권한(BUYER) 확인 → 판매자 존재 확인 → 미팅 요청 생성(status=REQUESTED) → 판매자에게 알림(NOTI-004)
- **출력**: 생성된 미팅 요청
- **예외**: 미인증 401 / 권한없음 403 / 판매자 없음 404 / 입력오류 400 `VALIDATION_ERROR`
- **응답 흐름**: 판매자가 MEET-003으로 수락(택일)·거절·재제안 → 확정 시 MEET-005(CONFIRMED) → 종료 시 MEET-006(COMPLETED/CANCELED)
- **연관**: MEET-002~006, NOTI-004

## 7. 공통 응답/에러 규약

- 모든 응답: `{ success, code, message, data }`
- 성공: `success=true, code="OK"`
- 실패 코드: `VALIDATION_ERROR`(400) / `BAD_REQUEST`(400) / `UNAUTHORIZED`(401) / `FORBIDDEN`(403) / `NOT_FOUND`(404) / `CONFLICT`(409) / `INTERNAL_ERROR`(500)
- 응답 메시지는 일반화(내부 상세 비노출), 상세는 서버 로그에만 기록
